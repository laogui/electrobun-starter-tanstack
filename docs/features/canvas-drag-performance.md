# 画布拖动性能检查（2026-09-18）

## 已确认的问题与修复

1. `useHelperLines` 更新坐标后，`useNodeDrag` 再执行高亮与排斥。两者即使没有改变任何节点，也生成新数组；`setNodes` 又总是发布新状态。现在高亮、排斥和 store 都保留无变化时的引用，避免空更新通知。
2. 排斥求解每轮遍历全部节点对，最多 32 轮。现在维护已激活节点的有序索引，跳过双方均未受影响的节点对，并保留原有求解顺序。单节点在稀疏画布中移动的配对扫描降为线性；大量节点同时被推挤时仍可能接近平方复杂度。
3. 路由装饰节点时，位置变化会重新创建 `data`。同时 React Flow 会把绝对坐标传给内容组件，导致普通 `memo` 失效。现在复用未变化的渲染数据，内容比较仅忽略 `positionAbsoluteX/Y`；尺寸、选中、拖动状态、内容和其他 props 仍会触发更新。坐标移动由 React Flow 外层负责。
4. 每个 Topic 的订阅各自构建整张主题树索引。现在共享索引，移动、缩放节点尺寸或改变选择不重建树；节点数据、类型、父容器及边发生变化时重新计算。
5. 关闭的素材库仍重建主列表和最近列表，关闭的搜索框仍重新排序最近节点。现在关闭时停止订阅这些节点数据。外围面板增加 memo 边界，底部切换器的 JSON 导出回调在点击时读取最新画布。

原有节点缓存已能保护多数静止节点，所以问题并非所有卡片每帧都重新渲染。持久化已有 2500 ms 防抖，普通连续拖动不会每帧序列化整张画布。

## 测量

本机 Bun 微基准：固定 700 单位间距，卡片尺寸 320×340，一张活动卡片；每个算法预热 30 次，采样 100 次。基线为本次修改前的 `repulsion.ts`，两个版本在同一进程测量。

| 节点数 | 原始中位耗时 | 优化后中位耗时 |
| --- | --- | --- |
| 500 | 0.349 ms | 0.131 ms |
| 1,000 | 1.012 ms | 0.262 ms |
| 2,000 | 3.843 ms | 0.501 ms |

2,000 节点场景的排斥计算耗时下降约 87%。100 节点场景耗时很小，索引管理没有带来可辨识收益。以上是求解函数测量，不代表整帧耗时或桌面应用 FPS。

另以固定随机种子生成 300 组 35 节点的密集场景，包含锁定节点、容器及两个活动节点，新旧算法输出完全一致。

## 回归验证

- `bun run test --maxWorkers=2`：237 files / 2255 tests 全部通过。日志有既有 jsdom navigation/media 未实现提示。
- `bun run type-check`、最终 `bun scripts/type-check.ts`、`bun run check`、`git diff --check` 通过。
- 内容 memo 测试：60 次纯坐标更新没有额外内容渲染；内容、选择、拖动结束和宽高变化仍正常渲染。
- 路由测试：60 次位置更新复用内容数据，编辑标题仍更新画面。
- React Profiler 测试：关闭的素材库和搜索框在 30 次位置更新中没有新增 commit；素材库重新打开读取最新内容。
- store 测试：无变化节点更新不通知订阅者，真实坐标变化正常通知。
- Chromium 开发页面：独立两卡片场景完成鼠标拖动；过程中坐标逐步更新，没有排斥空更新产生的重复坐标通知。松手落在启用的网格上，`dragging` 清除，远处卡片位置不变。松手阶段仍有状态收尾通知。

浏览器 HMR 会重置临时诊断 hook，因此未把浏览器临时 React hook 计数作为性能证据；重复渲染结论由回归测试和实际订阅链路支持。尚未测量 Electrobun 打包应用中的帧时间与 GPU 绘制开销。

# GhostBoard 笔记库弹窗（Library Popup）— 替代文档模式

> **状态**：Planned　**优先级**：P1
> **前置决策**：移除现有双布局文档模式（LayoutSwitcher + DocumentView 全家桶）
> **关联**：[PRD.md](../../PRD.md) §2.12 布局模式、[旧文档模式 spec](../Backlog/双布局-文档模式.md)（归档）

---

## 1. 背景与动机

当前应用实现了「画布 / 文档」双布局模式（`LayoutSwitcher` + `DocumentView`），但存在以下问题：

1. **增加了产品复杂度**——双模式意味着双份交互逻辑、状态冻结规则、键盘快捷键映射，维护成本高
2. **与市面产品同质化**——文档模式（左栏目录树 + 右栏编辑器）本质上和 Notion / Obsidian 没有差异，无法成为 GhostBoard 的差异化卖点
3. **半成品状态**——目录树、拖拽排序、右键菜单等核心交互未实现，给用户留下「承诺未兑现」的负面印象
4. **稀释了 canvas-first 定位**——用户在两种模式间切换时会产生认知割裂

**决策**：移除文档模式，代之以轻量的「笔记库弹窗」，解决用户的**浏览式发现**需求（"让我看看我有什么"），同时保持画布作为唯一的核心界面。

---

## 2. 用户故事

1. 作为一个画布用户，我希望不离开画布就能快速浏览当前画布上的所有笔记，找到我想编辑的那一篇。
2. 作为一个拥有大量笔记的用户，我希望能按文件夹分组查看笔记，并通过搜索快速筛选。
3. 作为一个画布用户，我点击笔记库中的某篇笔记后，画布能自动飞到那张卡片并打开聚焦编辑。
4. 作为一个拥有 detached notes（未放在画布上的游离笔记）的用户，我希望能在笔记库中看到它们并放回画布。

#### B. 新增笔记库弹窗（Library Popup）

- 画布左上角新增「笔记库」按钮
- 点击按钮弹出覆盖式弹窗（overlay modal），展示当前画布的所有笔记
- 弹窗内支持搜索筛选、排序、按 Folder 分组展示

- 笔记库内的拖拽排序 / 拖拽到画布
- 批量操作（多选删除、多选移动到 Folder）

**弹窗规格**：
- 尺寸：最大 `720px × 70vh`，居中
- 背景遮罩：`bg-black/40`，点击关闭

- 可通过 `Escape` 关闭

### 4.3 笔记卡片

每张卡片展示：
- 类型图标（📝 Note / ✅ Checklist / 🖼️ Image / 📎 Asset / 🔗 Link）
- 标题（截断 2 行）
- 更新时间（相对时间）
- 卡片颜色条（若有 `data.color`）

### 4.4 分组逻辑

按以下顺序展示：

1. **Folder 分组**——遍历当前画布中所有 `folder` 类型节点，每个 Folder 作为一个分组，标题为 Folder 名称，内含其 `data.children` 中的 Card / Image / Asset / Link
2. **未分组**——不属于任何 Folder 的顶层 `card` / `image` / `asset` / `link` 节点
3. **游离笔记**（仅当存在时显示）——`data.detached === true` 的节点

Sticky / Group / Edge **不在笔记库中显示**。

### 4.5 排序

顶部提供排序切换（下拉菜单）：
- 最近编辑（默认）—— `updatedAt` 倒序
- 名称 A–Z
- 创建时间

排序在每个分组内部生效。

### 4.6 搜索筛选

顶部搜索框对标题进行即时筛选（前端 filter，不走后端 RPC）。输入时隐藏不匹配的卡片，空分组自动隐藏。

### 4.7 点击行为

| 场景 | 行为 |
| --- | --- |
| 点击**顶层笔记卡片** | 关闭弹窗 → `fitView` 飞到该节点 → 自动打开 FocusedView |
| 点击 **Folder 内的子笔记** | 关闭弹窗 → 打开该 Folder 的 drill-down → 聚焦到子卡片 |
| 点击 **detached note** | 关闭弹窗 → toast 提示「此笔记尚未放置在画布上」+ 「放到画布」按钮 → 点击后 `pinNoteToCanvas` 放到视口中心 → 自动打开 FocusedView |
| 点击 **Image 类型卡片** | 关闭弹窗 → `fitView` 飞到该节点 → 自动打开 FocusedView（图片预览模式） |

#### 与既有入口的角色边界

| 入口 | 触发 | 角色 |
| --- | --- | --- |
| `Cmd/Ctrl+K` `SearchDialog` | 关键词驱动 | **「我知道我要什么」**——按标题/正文搜索，跨画布跳转 |

首版决定（避免角色冲突）：

- **Library 弹窗中的 detached 区只读 + 跳转**——点击 detached 卡片走 toast 提示「此笔记尚未放置在画布上」+「放到画布」按钮，按钮内部复用 `pinNoteToCanvas`，操作语义不绕过 Sidebar 体验

- 若用户实际打开 Library 后频繁要做 detached 管理，未来再考虑用 Library 取代 Sidebar（见 §10）

### 5.6 useLibraryData hook 逻辑

复用 `@/lib/canvasNodePredicates` 已有的 `isFocusableNode`（其类型集合恰好是 `card | image | asset | link`，与首版 Library 收录范围一致），避免硬编码字符串数组：

```ts
import { isFocusableNode } from '@/lib/canvasNodePredicates';

// 从 store nodes 派生分组数据
function useLibraryData() {
  const nodes = useCanvasStore((s) => s.nodes);
  return useMemo(() => {
    const folders = nodes.filter((n) => n.type === 'folder');
    const groups = folders.map((f) => ({
      id: f.id,
      name: (f.data as any).title,
      items: ((f.data as any).children ?? []).filter((c: any) =>
        isFocusableNode(c.type)
      ),
    }));

    const folderChildIds = new Set(
      groups.flatMap((g) => g.items.map((i: any) => i.id))
    );
    const ungrouped = nodes.filter(
      (n) =>
        isFocusableNode(n.type) &&
        !(n.data as any)?.detached &&
        !folderChildIds.has(n.id)
    );
    // 与 DetachedNotesSidebar 现状对齐：首版仅展示 card / image 的 detached
    const detached = nodes.filter(
      (n) =>
        (n.type === 'card' || n.type === 'image') &&
        (n.data as any)?.detached
    );

    return { groups, ungrouped, detached };
  }, [nodes]);
}
```

### 5.7 「点击卡片 → 飞到节点 → 打开 FocusedView」的异步编排

这是被早期版本忽略的关键执行细节。`setFocusedNode` / `setFocusedFolder` 的入参必须包含 `rect: DOMRect`（FocusedView / FolderView 的进出动画就是从这个 rect 缩放到聚焦态），而 `rect` 来自节点的真实 DOM；如果节点离开视口被 React Flow culling，DOM 根本不存在；即便在视口内，刚 `setCenter` 时也还在 240ms 飞行动画中。

建议抽取到 `src/mainview/lib/canvasFocus.ts`，被 `LibraryPopup`、`DetachedNotesSidebar`、`SearchDialog` 共同复用：

```ts
export interface OpenFocusedOptions {
  nodeId: string;
  rfInstance: ReactFlowInstance<any, any> | null;
  /** Optional: 在 fitView 完成后再调用 setFocusedNode 的等待时长。 */
  centerDurationMs?: number;
}

export async function openFocusedById({
  nodeId,
  rfInstance,
  centerDurationMs = 240,
}: OpenFocusedOptions): Promise<void> {
  const { nodes, setFocusedNode, setFocusedFolder } =
    useCanvasStore.getState();
  const node = nodes.find((n) => n.id === nodeId);
  if (!node) return;

  // 1. setCenter 触发飞行动画
  const w =
    (node as any).measured?.width ?? (node as any).width ?? 320;
  const h =
    (node as any).measured?.height ?? (node as any).height ?? 160;
  const zoom = rfInstance?.getViewport?.()?.zoom ?? 1;
  rfInstance?.setCenter?.(
    node.position.x + w / 2,
    node.position.y + h / 2,
    { zoom, duration: centerDurationMs }
  );

  // 2. 等飞行结束 + 一帧 layout flush，再去取真实 rect
  await new Promise((r) => setTimeout(r, centerDurationMs + 16));

  // 3. 优先从 DOM 取 rect（精确）；DOM 不在时按 viewport 推算（兜底）
  const el = document.querySelector(
    `[data-id="${nodeId}"]`
  ) as HTMLElement | null;
  const rect =
    el?.getBoundingClientRect() ??
    computeRectFromViewport(node, rfInstance, w, h);

  if (node.type === 'folder') {
    setFocusedFolder({ id: node.id, data: node.data, rect });
  } else {
    setFocusedNode({
      id: node.id,
      type: node.type,
      data: node.data,
      rect,
    });
  }
}
```

Folder 子卡片的「打开 drill-down → 聚焦子卡」更复杂：`FolderView` 子卡 focus 是通过其内部 `onCardClick` 回调触发的，外部无法直接同时打开 folder 并聚焦子卡。两种实现方案：

- **方案 A（首版推荐，简单）**：Library 中点击 Folder 内笔记 → 关闭弹窗 → `openFocusedById(folderId)` 仅打开 drill-down，由用户在 drill-down 视图里再点子卡进入 FocusedView。
- **方案 B（体验更好）**：在 `canvasStore` 增加 `pendingFocusedChild: { folderId: string; childId: string } | null` 状态；`openFocusedById` 同时 `setPendingFocusedChild`，`FolderView` 在挂载完成后消费一次该状态、调用自身的 `setFocusedNode({ ..., folderId, rect })` 并清空 pending。

首版采纳方案 A；若用户反馈强烈再升级为方案 B（不破坏 store 形状）。

## 7. 风险与权衡

| 风险 | 应对 |
| --- | --- |
| 移除文档模式后，现有用户（如果有）习惯被打破 | 产品尚在 alpha 阶段，用户量极少；文档模式本身是半成品，切换成本可接受 |
| 笔记库弹窗无法替代长文编辑场景 | 长文编辑由 FocusedView 承担，与笔记库是互补关系 |
| Detached notes 在弹窗中无法直接编辑 | 提供「放到画布」一键操作，放回后即可通过 FocusedView 编辑 |
| 笔记量大时（>200）卡片网格性能 | 首版用 CSS Grid + overflow-y-auto；若出现性能问题，后续接入 `@tanstack/react-virtual` |
| 删除大量代码可能引入回归 bug | 见下方「执行节奏」——必须拆成两个 PR 串行合入 |
| 「关闭弹窗 → fitView → 打开 FocusedView」的异步编排出错 | 见 §5.7；`openFocusedById` 需要等待 240ms 飞行动画完成才能取 rect，否则 FocusedView 进场动画会从错误起点开始；DOM 兜底逻辑不能漏 |

#### 执行节奏（PR 拆分）

**必须拆成两个 PR 串行合入**，避免主分支停留在「文档模式没了，但 Library 也还没有」的产品退化态：

- **PR-1：移除文档模式**（对应 M1）
  - 完成 §3.1 A 所有删除 + §5.2「PRD / tech-spec 清理清单」
  - 合入条件：`bun run ci` 通过 + `bun run test` 全绿 + 手测「画布渲染正常、`Cmd+K` 搜索正常、Sidebar 放回画布正常」
  - 合入后主分支处于「只有画布、无 Library 入口」的可发布中间态
- **PR-2：新增 Library Popup**（对应 M2–M5）
  - 在 PR-1 之上加 `LibraryButton` / `LibraryPopup` / `useLibraryData` / `openFocusedById` 工具
  - 合入条件：覆盖 §8 全部验收标准

两个 PR 都不应大到无法 review；PR-1 主要是删除 + 文案修订，PR-2 主要是新增 + 异步编排逻辑。

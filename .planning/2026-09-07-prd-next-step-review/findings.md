## T6 Findings

- T6 is exactly as documented: `src/bun/search.ts` privately owns both mappings while `src/shared/extensions/builtinIds.ts` already owns the stable IDs and the reverse legacy-kind-to-ID helpers.
- The shared module cannot import Bun's `SearchResultKind` or `WidgetKind` without reversing the dependency boundary. It should export narrow shared literal unions for the mapped display kinds and legacy Productivity kinds; those are structurally assignable to the Bun search result types.
- Direct mapping coverage belongs in `builtinIds.test.ts`; existing `search.test.ts` remains the end-to-end consumer regression. Each published built-in plus an unknown third-party ID should be asserted so adding a built-in cannot silently default to `extension`.
- The first mapping test did not run because Vitest's include globs omit `src/shared/**`; the pre-existing `src/shared/extensions/builtinIds.test.ts` has therefore never been part of `bun run test`. T6 cannot claim centralized mapping coverage unless this collection gap is fixed or the tests are relocated to a collected boundary.
- There are nine pure Node-compatible shared extension test files, covering IDs, instances, migration, refs, presentation, enablement, and Productivity state. Adding `src/shared/**/*.{test,spec}.{ts,tsx}` to the existing Node Vitest project is low-risk and restores intended coverage beyond T6 itself.
- Coverage globs should be synchronized with test collection so shared source is measured and shared test files excluded consistently; otherwise the config would continue treating the shared boundary as invisible.
- The centralized implementation uses an exhaustive `Record<BuiltinCanvasTypeId, ...>` for search display kinds, so TypeScript forces every newly added published built-in ID to receive an explicit mapping. Unknown/external IDs retain the generic `extension` fallback; only Productivity IDs receive a legacy widget badge kind.

## D1-1 Findings — Search Target Contract

- The Bun searcher already walks top-level manifest nodes and one level of `folder.data.children`; Folder Widget and Extension children are indexed by joining their sidecar/instance content back to a synthesized `nodeId`.
- `SearchResult` currently carries `viewId`, `nodeId`, `edgeId`, and optional `noteId`/`widgetId`, but no owner-container identity or target category. A Folder child therefore looks identical to a top-level node once it reaches the renderer.
- `SearchDialog.locateInCurrentView` selects and centers only a top-level React Flow node. The cross-view `pendingSearchTarget` effect repeats the same flat lookup after hydration. A Folder-child result can be searchable and selectable in the dialog, but cannot select/open its hidden child from that flat contract.
- `FolderView` receives the owning folder node and renders child entries from `folder.data.children`; the existing focus state supports `focusedFolder` plus an optional `folderId` on a focused child. This is the seam for D1-2 navigation, but D1-1 should first make the target identity explicit without inventing a second content database.
- The same-view memory fallback in `useSearch.searchCurrentView` currently scans only top-level nodes and does not include extension presentation or Folder children. It can supplement backend results for unsaved top-level nodes, but its scope must be declared instead of silently claiming complete Folder reachability.
- Search results group by `viewId` and deduplicate by generated result id. Any target extension must keep stable result IDs per view/container/content reference so repeated Note views and multiple Folder references are not collapsed incorrectly.
- The D1-1 implementation boundary should add serializable target metadata (`targetType`, `containerId`, `containerType`, and a stable content reference) to the shared search result contract, populate it for backend Folder children, and preserve existing top-level behavior. D1-2 can then consume the contract to enter the correct Folder and open/select the child.

## D1-2 Findings — Folder Hit-to-Open Navigation

- Folder expansion is implemented as render-only React Flow nodes with ids of the form `folderExpandedChild:{folderId}:{childId}`. The existing `openNodeFocusedView` helper already knows how to convert that node back into `FocusedItem { id, folderId, type, data, rect }` and respects `isFocusableNode`.
- The route-level pending-search effect is the correct cross-view seam: it runs only after the destination manifest is hydrated. Folder targets now resolve in three steps—validate the owner and child reference, enter the owner Folder, then resolve the expansion node and open it. A missing owner/child clears the stale target instead of leaving navigation blocked.
- Non-focusable legacy children (for example a stored `widget`) remain visible in the opened Folder layer and are not coerced into FocusedView. This preserves the existing “canvas interaction in place” behavior while still making the hit reachable.
- Folder Card children were not part of the backend Note reference map. D1-2 now synthesizes a Folder-child `NodeRef` for every valid child, joins `noteId` to sidecar/legacy records, and reuses manifest metadata matching for media/link/card children. Widget and Extension bodies continue through their dedicated stores.
- Same-view Folder hits are routed through the same pending-target state as cross-view hits, so SearchDialog does not attempt to select a hidden child as though it were a top-level canvas node. Cross-view save-before-switch remains owned by `switchView`; route tests simulate the post-switch hydration boundary.

## D2-3 Findings — Failure Paths and Persistence Boundary

- Missing local media fails visibly: removing `attachments/d2-research-report.pdf` and opening the same Folder child in FocusedView produced `Media file could not be loaded.`; restoring the exact file restored the fixture. This is a non-blocking, recoverable missing-file path.
- Byte-level corruption reproduced a separate issue: replacing the PDF with ASCII text left WebKit showing a blank iframe with no error. `AssetNode.tsx` now validates the bounded data-URL prefix for `%PDF-` before mounting the iframe and routes invalid content through the existing explicit media-error surface. The desktop retest showed `Media file could not be loaded.` and `AssetNode.test.tsx` covers the invalid data URL; the original fixture PDF was restored.
- Link preview failure is explicit and scoped. Saving a temporary `https://offline.invalid/d2/evidence` URL produced `Retry preview` plus `Preview unavailable`; the original URL and ready metadata were restored in the fixture. The renderer keeps the link and URL usable even when remote metadata cannot be fetched.
- Cross-view deletion preserves shared content identity. Removing the Delivery reference to `note_d2_shared` did not remove Research's reference or the sidecar; restoring the Delivery manifest and restarting returned both references. This confirms deletion is reference-scoped, not a silent global content delete.
- Immediate undo followed by a full restart preserved the deleted reference on disk and in the UI. The transient toast after undo was stale but did not affect data; no product change was justified by this run.
- An unwritable export directory produced the native `EACCES` path in the notification and no output file. The export action did not report success falsely; restoring directory permissions returned the normal path.
- A real title-only BlockNote persistence gap was found during the save-failure audit. The title textarea called the parent callback but never entered the editor's content-save path, so a title-only blur could look edited while the sidecar stayed unchanged. The fix tracks title dirtiness, serializes current blocks/Markdown on blur, queues the save, and flushes it. A jsdom integration regression and desktop sidecar revision check now cover it.
- When the BlockNote sidecar directory was made non-writable, the same title-only operation showed `Save failed` and `Could not save this note. We'll retry on your next edit.`; restoring permissions and editing again succeeded. This provides an actionable recovery path rather than a false saved state.
- The tested paths do not justify a new D3 interaction. The boundary is explicit: BlockNote local editing remains on the local sidecar RPC with AI disabled, Link metadata fetch failures stay visible as `failed`/`Preview unavailable`, and the local AI endpoint returns a CORS-enabled `503` when no provider is configured. No provider credentials were available, so no live-provider behavior is claimed; keep the public-plugin track separate.
